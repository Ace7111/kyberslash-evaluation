# Reproduction Guide

Every table and figure in the dissertation is regenerated by the commands below. The
guide assumes a clean host. The labelled steps sum to about thirty-five minutes; allow
roughly forty end to end, since cloning the four upstream repositories in steps 2, 6 and 6b
adds time that depends on your connection.

## 0. Requirements

| Requirement | Used here | Notes |
| --- | --- | --- |
| macOS or Linux | macOS 25.3.0 (Darwin), arm64 | Linux works; see platform notes |
| GCC | 16.1.0 (Homebrew) | `brew install gcc` — macOS `gcc` is Clang and will not do |
| Clang | Apple Clang 17.0.0 | ships with Xcode Command Line Tools |
| Python | 3.12.3 | standard library only; no third-party packages |
| git | 2.50.1 | |
| objdump | Apple LLVM 17.0.0 | LLVM or GNU binutils both work |

No third-party Python packages are required. This is deliberate: the analysis must run
years from now without a dependency resolver.

```sh
brew install gcc cmake ninja      # macOS
# apt install gcc clang python3 binutils git   # Debian/Ubuntu
```

## 1. Capture the environment

Run once per measurement session. Timing results are only interpretable alongside the
host state that produced them.

```sh

# -> results/logs/system_manifest_<UTC timestamp>.txt
```

## 3. Build and audit the matrix (~10 min)

```sh
python3 scripts/build_matrix.py
```

Per cell this creates a worktree, compiles, runs the upstream functional test, then
disassembles the binary and attributes every division to its containing function. Cells
are gated: a build or functional failure records `gate_failed_at` and yields no security
verdict.

Expected: 24 cells, all building and passing functional tests. `VULNERABLE` in exactly
four — `kyber-vulnerable` under GCC `-Os`, GCC `-Oz`, Clang `-O0` and Clang `-Oz`.

Then audit the **current** reference HEAD, which is the revision RQ2 actually asks about
and where a reader will look first:

```sh
python3 scripts/build_matrix.py --targets kyber-current \
  --out results/processed/build_matrix_current.json
```

Expected: 12 cells, all clean. Incidental divisions remain (3 at GCC `-Os`/`-Oz`, 19 at
Clang `-O0`) in Keccak and `gen_matrix`; `secret_div` must be 0 everywhere.

```sh
# Audit any single binary
python3 scripts/inspect_binary.py results/builds/<cell>/test_kyber
```

## 4. Confirm the host divider behaviour (~1 min)

This step decides how the timing results must be reported, so do not skip it.

```sh
clang -O2 scripts/udiv_latency.c -o /tmp/udiv_latency && /tmp/udiv_latency
clang -O2 scripts/udiv_ecore.c   -o /tmp/udiv_ecore   && /tmp/udiv_ecore
```

On Apple M1 every operand pair returns ≈2.81 ns regardless of quotient width, on both core
types: the divider is constant-latency. On a host with an early-terminating divider
(Cortex-A7/M4, and many x86-64 cores for `div`) the 32-bit-quotient row is markedly slower.
Record which case applies — it determines whether the `host_ns` column carries signal.

## 5. Leakage screening (~5 min)

```sh
# Instrument, build and run the vulnerable revision
python3 scripts/make_instrumented.py worktrees/kyber-vulnerable/ref /tmp/ks_instr_vuln
cp harness/timing_harness.c /tmp/ks_instr_vuln/
(cd /tmp/ks_instr_vuln && gcc-16 -w -O2 -DKYBER_K=3 -I. \
   kem.c indcpa.c polyvec.c poly.c ntt.c cbd.c reduce.c verify.c \
   fips202.c symmetric-shake.c randombytes.c timing_harness.c -o timing_harness \
 && ./timing_harness 40000 2000 20260801 > /tmp/vuln.csv)

python3 scripts/analyse_results.py /tmp/vuln.csv \
  --experiment-id EXP-LEAK-vuln-gcc16-O2-seed20260801
```

Repeat with `worktrees/kyber-patched/ref` for the paired mitigation condition.

`make_instrumented.py` reports sites per variant: 1 KyberSlash1 and 4 KyberSlash2 for the
vulnerable revision, 0 and 0 for the patched one. It tracks the enclosing function, tolerates
the optional space in `/ KYBER_Q` (present in the `KYBER_K * 320` branch of `polyvec_compress`
that ML-KEM-768 actually compiles), skips commented-out originals, and exits non-zero if any
runtime division is left untransformed.

Arguments are `timing_harness <samples> <warmup> [seed]`. The seed fixes class assignment,
so a rerun with the same seed reproduces the same class sequence.

### Expected results

Vulnerable, 40,000 samples, ML-KEM-768, GCC 16.1.0 `-O2`:

With seed `20260801` — the third positional argument to `timing_harness` above. It is not
optional for reproduction: omit it and the harness falls back to its built-in default
`0x5eed1234`, which is a different key and gives different numbers.

| Column | Difference in means | Welch t | Cohen's d | Decision |
| --- | --- | --- | --- | --- |
| `ks1_cycles` | +58.46 | 1005.97 | 9.98 | LEAKAGE DETECTED |
| `ks2_cycles` | +21.95 | 70.05 | 0.70 | LEAKAGE DETECTED |
| `modelled_cycles` (sum) | +80.41 | 252.86 | 2.51 | LEAKAGE DETECTED |
| `host_ns` | +23.99 | 1.02 | 0.010 | not detected |

**Do not generalise from one key.** KyberSlash2's *sign* depends on the key — it is
negative for 4 of the 10 seeds swept in `docs/findings.md` F3. Run the sweep before
drawing any conclusion about the aggregate:

```sh
python3 scripts/seed_sweep.py /tmp/ks_instr_vuln/timing_harness --samples 20000 \
  --json-out results/processed/seed_sweep_vulnerable.json
```

Call counts should read `ks1_calls=256`, `ks2_calls=1024`. Anything else means a division
site was missed.

Patched: zero on both modelled columns (no runtime division remains) and t ≈ −0.55 on
`host_ns`.

**Same seed, same numbers.** The harness supplies its own deterministic `randombytes()`,
so the keypair and fixed ciphertext are derived from the seed. A rerun with the same seed
reproduces these figures exactly; verify the archived datasets with
`shasum -a 256 -c results/raw/SHA256SUMS`.

**Different seed, different key — and KyberSlash2 may change sign.** Across keys,
`ks1_cycles` is reliably positive with |d| between 8 and 13, while `ks2_cycles` ranges
from d = −1.14 to +2.13. Report the sweep, not a single key.

## 5b. Divider-model sensitivity (~4 min)

The modelled columns assume one divider model. If a conclusion held only under that exact
parameterisation it would be an artefact of the assumption, so vary it:

```sh
python3 scripts/model_sensitivity.py /tmp/ks_instr_vuln \
  --json-out results/processed/model_sensitivity.json
```

Six models over four seeds, 20,000 samples each — the defaults, which are what the archived
file records. Each model is applied by **rebuilding** the harness with different `-D`
constants and re-measuring. Do not re-cost already-collected totals instead: the clamp is
non-linear and KyberSlash2 divisions do reach it, so applying a clamp to a mean is not the
mean of the clamped values.

Expected: `ks1_positive_all_models` and `ks1_detected_all_models` true,
`ks2_sign_stable_across_models` false, and `flat_control_null` true. The `flat` model is a
control — division *count* is constant per decapsulation, so a non-zero effect there would
indicate a counting bug rather than leakage.

## 6. RQ1 and RQ3 targets (~10 min)

```sh
# RQ1 - contemporary FIPS 203 implementation
git clone https://github.com/pq-code-package/mlkem-native.git targets/mlkem-native
cd targets/mlkem-native && git checkout 61c831345d8fec5b2ba9d727dddb486b7cce512a && cd ../..

python3 scripts/audit_rq1_rq3.py     # writes one record per cell, with binary hashes
```

**Setting the optimisation level here is a trap; read this before changing it.**
`test/mk/config.mk` builds its own `CFLAGS` with `-O3` hard-coded, ending `... $(CFLAGS)`.

  * A command-line `CFLAGS=` overrides the whole assignment, discarding the required
    flags; every build then fails with a missing `mlkem_native_config.h`.
  * Putting the flag inside `CC` compiles as `gcc-16 -O0 -O3`. The last `-O` wins, so
    every build is `-O3` whatever was asked for. This yields twelve byte-identical
    binaries and a sweep that varied nothing — see D7 in findings.md.
  * Passing it through the **environment** expands into the trailing `$(CFLAGS)`, landing
    after `-O3`, and wins. That is what the script does.

Check with `CFLAGS=-O0 make func CC="gcc-16 -w" -n`: the compile line must end `-O3 -O0`.

Expected: 12/12 build and pass functional tests, zero *secret-dependent* divisions in
every cell, and incidental divisions in four (GCC `-Os`/`-Oz`, Clang `-O0`/`-Oz`).
Eleven of the twelve binaries are distinct; GCC `-Os` and `-Oz` coincide.

```sh
# RQ3 - independent Go implementation
git clone https://github.com/cloudflare/circl.git targets/circl
cd targets/circl && git checkout df9fbeabf921471216232de66f0392196dcdc37c && cd ../..
```

Build a probe binary against it (see `docs/findings.md` F5), run it, then:

```sh
python3 scripts/inspect_binary.py /tmp/circl_probe/circl_probe
```

Expected: `NO_SECRET_DEPENDENT_DIV`, 0 secret-dependent divisions, 43 total (Go runtime).
Confirm `(*Poly).CompressTo` and `(*Vec).CompressTo` appear in `nm` output — if the
compression symbols were inlined away, a null result would be meaningless.

## 6b. wolfSSL (RQ3, second independent implementation) (~2 min)

**Provenance of this section.** The original wolfSSL audit (2026-08-02, commit `1d333cf`)
was performed by hand and no script was written for it at the time. What the original run
recorded is the `build_note` in `configs/targets.yaml`: the file audited, the defines used,
and the fact that autotools was unavailable so the audit was done at object level rather
than against a linked library. The commands below were reconstructed from that note on
2026-09-06 and validated against the pinned source. They are **later reproducibility
tooling, not a transcript of the original session.**

The note's define list is necessary but not sufficient: `wc_Sha3` and `wc_Shake` are
declared in `wolfssl/wolfcrypt/sha3.h` behind `WOLFSSL_SHA3`, and reaching them requires a
settings header. A minimal `user_settings.h` with `-DWOLFSSL_USER_SETTINGS` is enough.

```sh
git clone https://github.com/wolfSSL/wolfssl.git targets/wolfssl
cd targets/wolfssl && git checkout 7a8aae3e40138d19c640ae5bc0bc4e8f2998c22d && cd ../..

mkdir -p /tmp/wolfcfg && cat > /tmp/wolfcfg/user_settings.h <<'H'
#define WOLFSSL_SHA3
#define WOLFSSL_SHAKE128
#define WOLFSSL_SHAKE256
#define WOLFSSL_HAVE_MLKEM
#define WOLFSSL_WC_MLKEM
H

DEFS="-DWOLFSSL_HAVE_MLKEM -DWOLFSSL_WC_MLKEM -DWOLFSSL_SHA3 -DWOLFSSL_SHAKE128 -DWOLFSSL_SHAKE256"
for opt in -O2 -Os; do
  for cfg in "" "-DCONV_WITH_DIV"; do
    gcc-16 -c -w $opt -DWOLFSSL_USER_SETTINGS $DEFS $cfg \
      -I/tmp/wolfcfg -Itargets/wolfssl \
      -o /tmp/wolf.o targets/wolfssl/wolfcrypt/src/wc_mlkem_poly.c
    echo "$opt ${cfg:-default}"
    python3 scripts/inspect_binary.py /tmp/wolf.o
  done
done
```

Expected, and confirmed by the 2026-09-06 validation run:

| Configuration | `-O2` | `-Os` |
| --- | --- | --- |
| default | 0 | 0 |
| `-DCONV_WITH_DIV` | 0 | **48** |

The 48 localise to `mlkem_to_msg` (KyberSlash1) and `mlkem_compress_4`, `mlkem_compress_5`,
`mlkem_vec_compress_10`, `mlkem_vec_compress_11` (KyberSlash2). At `-O2` the same flag
yields zero because the compiler strength-reduces the divisions away, so the build flag and
the optimisation level are jointly necessary — which is the point of the finding.

Note the scope: this audits one translation unit, not a linked library. §6.8 records that
limitation.

## 7. Clangover check (~2 min)

```sh
git -C targets/pq-crystals-kyber worktree add -f \
  ../../worktrees/kyber-clangover-fixed 9b8d306

for rev in kyber-patched kyber-clangover-fixed; do
  (cd worktrees/$rev/ref && clang -w -O2 -DKYBER_K=2 -c poly.c -o /tmp/$rev.o)
  objdump -d /tmp/$rev.o | awk '/poly_frommsg>:/{f=1} /^[0-9a-f]+ </{if(f && !/poly_frommsg>:/)f=0} f'
done
```

Do not read the branch *count* as a result. On aarch64 the pre-fix build has three
conditional branches at `-O2` and the post-fix build has one, which looks like a
regression and is not: inspect each branch. All three are benign (one vectoriser
pointer-alias check, two loop counters) and the scalar path keeps the branchless mask
`sbfx w11, w11, #0, #1`. See `docs/findings.md` F6.

## 8. Regenerate archived outputs

The archived datasets carry the seed in the filename, because a different seed is a
different key and the two must never be conflated:

```sh
for cond in vuln patched; do
  python3 scripts/analyse_results.py \
    results/raw/EXP-LEAK-$cond-gcc16-O2-seed20260801.csv \
    --experiment-id EXP-LEAK-$cond-gcc16-O2-seed20260801 \
    --json-out results/processed/EXP-LEAK-$cond-gcc16-O2-seed20260801.json
done

shasum -a 256 -c results/raw/SHA256SUMS   # verify archived raw data is unmodified
```

Run the regression tests before trusting an audit result:

```sh
python3 tests/test_classify.py
# -> 31/31 classifier cases passed
#    4/4 disassembly-parsing cases passed
```

Add `--bootstrap` for a percentile bootstrap CI instead of the analytic Welch interval.
The two agree to within reporting precision at these sample sizes; the analytic form is
the default because it takes milliseconds rather than minutes.

## 9. Regenerating the figures

Figure 5.1 is generated from the measurement data, so it cannot drift from the numbers it
depicts:

```sh
python3 scripts/make_figure_5_1.py           # -> results/figures/figure_5_1_effect_by_key.svg
python3 scripts/make_presentation_figures.py # -> results/figures/figure_p1_*.svg, figure_p2_*.svg
```

Both write SVG only. The PNGs alongside them were produced with
`rsvg-convert -z 2 -b white -o results/figures/NAME.png results/figures/NAME.svg`.

Figures 2.1, 2.2 and 4.1 are Mermaid diagrams. `scripts/render_figures.sh` renders them,
but note its input: it reads `../dissertation/figures.md`, which lives in the dissertation
working tree and is **not** part of this repository. From a standalone clone of the
artefact the script has nothing to render, and the committed SVGs and PNGs under
`results/figures/` are the record.

If you do have the sources, note the trap the script exists to avoid: Mermaid's default
`htmlLabels: true` puts every label inside an SVG `<foreignObject>`. Browsers render that;
`rsvg-convert` and most other rasterisers drop it silently, yielding a PNG of correctly
laid-out but completely empty boxes — which is what reached figures 2.1, 2.2 and 4.1 in an
earlier run. `render_figures.sh` therefore renders with `htmlLabels: false` and refuses to
rasterise an SVG containing no `<text>` element. `scripts/svg_inline_labels.py` is the
recovery path for an SVG that was already rendered the wrong way and cannot be re-rendered:
it lifts the label text out of each `<foreignObject>` and re-emits it as SVG text.

## Platform notes

**The modelled column is a simulation.** `modelled_cycles` applies the divider model in
`harness/ks_instrument.h` (Cortex-M4, 2–12 cycles, ~1 quotient bit per cycle after setup).
It quantifies the leak the *operands* carry and is independent of host divider behaviour.
It is not a measurement of any physical device and must never be reported as one. The
model's constants are exposed precisely so a sensitivity analysis can vary them.

**The host column is a real measurement**, and on a constant-divider host it correctly
shows no leakage. That divergence is a finding, not a fault: see `docs/findings.md` F2/F3.

**On x86-64 Linux**, `div`/`idiv` latency is operand-dependent on many cores, so `host_ns`
may itself show the leak. `inspect_binary.py` already searches `div`/`idiv` when it detects
an x86-64 host. Re-run step 4 there to confirm before interpreting the host column.

**The x86-64 evidence in this repository is a binary audit, not a timing measurement.** It
was produced by GitHub Actions on `ubuntu-latest`, not on the Apple M1 host, and it is
archived rather than regenerated by the steps above:

| What | Where |
| --- | --- |
| 14 per-cell audit records | `results/processed/build_matrix_x86_64_ci.json` |
| Toolchain and runner provenance | `results/logs/x86_64_ci_toolchain_20260802T155008Z.txt` |
| Full original CI transcript | `results/logs/x86_64_ci_run30755244934_full.log` |
| Workflow that produced it | `.github/workflows/constant-time-audit.yml` |

To regenerate it, run that workflow on an x86-64 runner; running `build_matrix.py` locally
on this aarch64 host will not reproduce those cells. Note that the workflow targets
`ubuntu-latest`, which resolved to `ubuntu-24.04` with GCC 13.3.0 and Clang 18.1.3 on
2026-08-02 and will not stay pinned there — the toolchain provenance file, not the
workflow, is the record of what actually produced these results.

Architecture and compiler release vary together between the aarch64 and x86-64 sets, so the
two are not a clean single-factor comparison — see `docs/findings.md` F7.

## Safety

All experiments run locally against researcher-generated synthetic keys. Nothing in this
repository contacts a network service, and no third-party or public ML-KEM deployment is
tested. Conducted under Manchester Metropolitan University EthOS approval.
